## 引言
控制器局域网（CAN 总线）几乎是所有现代车辆和复杂机器的[中枢神经系统](@entry_id:148715)，负责协调刹车、发动机和安全气囊等关键部件之间的通信。然而，这个无处不在的协议是在一个隔离、可信的系统时代设计的，这使其从根本上无法应对当今互联世界的威胁。这种固有的安全性缺失在网络功能与信息物理系统所需的安全保障之间造成了巨大鸿沟。本文通过全面探讨 CAN 总线安全，从其协议层面的缺陷到现代硬件和软件中所需的复杂多层防御，旨在弥合这一鸿沟。

在接下来的章节中，我们将首先解构 CAN 协议的核心“原理与机制”，揭示其优雅设计如何同时成为其最大弱点，并探讨用于在其之上构建数字盾牌的密码学技术。随后，在“应用与跨学科联系”部分，我们将拓宽视野，探讨如何将保障 CAN 总线安全视为一个更大难题中的一小部分，深入研究定义现代汽车网络安全的 ECU 安全、软件完整性和硬件级防御等相互关联的挑战。

## 原理与机制

要真正理解控制器局域网（CAN 总线）的安全挑战，我们必须首先欣赏其优美而简约的设计。想象一下，它不是一个复杂的计算机网络，而是一种更为基本的形态：一根单独的电线，一个共享信道，就像一条多人共用的电话线，许多人可以说话，但一次只能有一个人说。CAN 的精妙之处在于它如何在没有中央仲裁者的情况下解决了这个“谁可以发言”的问题。这是一曲去中心化协作的交响乐，但其优雅之处也正是其漏洞的根源。

### 单线上的交响乐

CAN 总线基于一个简单的物理原理运行。总线有两种状态：**隐性**状态，你可以将其理解为一个安静的“1”；以及**显性**状态，一个响亮的“0”。规则很简单：如果总线上的任何设备发送一个显性的“0”，整条线路就会变为“0”，压制任何隐性的“1”。这就像一场大声嚷嚷的比赛，其中“不”（显性的 0）这个词总比“是”（隐性的 1）更响亮。

这如何防止所有人同时说话呢？通过一个称为**逐位仲裁**的过程。当多个设备或**节点**想要发送消息时，它们会同时开始传输，从消息的**标识符** (ID) 开始。在传输每一位时，它们也会监听总线。如果一个节点传输了一个安静的“1”，但在总线上听到了一个响亮的“0”，它就知道有其他设备正在发送一个更“显性”的消息。它会立即停止发送，并等待下一次发言的机会。

这个简单且非破坏性的过程带来了一个深远的结果：ID 数值较小的消息拥有更多的前导零。由于“0”是显性的，这些消息将总能在仲裁竞赛中获胜。一个 ID 为 `0x100` (`0001...`) 的消息总会胜过一个 ID 为 `0x200` (`0010...`) 的消息，因为它能在序列中更早一位“喊出”它的显性零。因此，消息 ID 决定了其**优先级**。这种优雅的、由硬件强制执行的优先级方案是 CAN 实时性能的核心  。该系统确保了最关键的消息——比如刹车指令——永远不会被次要数据所延迟。

### 信任的原罪

CAN 协议诞生于一个纯真的年代，专为机器内部的封闭世界而设计，在这个世界里，所有组件都是值得信赖的合作者。协议的设计者从未设想过一个组件可能会背叛另一个组件的场景。这种基于信任的基础假设是其所有安全弱点的根源。

首先，消息 ID 并不标识**发送者**，而是标识**内容**。ID `0x123` 并不意味着“来自发动机 ECU”，而是意味着“此消息包含发动机转速数据”。总线上的任何节点都可以发送 ID 为 `0x123` 的消息。协议没有提供内置方法来验证消息的真实来源，这项安全服务被称为**认证**。任何节点都可以冒充另一个节点，这是一种称为**欺骗**的基本攻击  。标识符用于仲裁和消息类型，而不是用于对发送者身份进行加密验证 。

其次，没有保密性。所有通信都是广播的。任何节点发送的每条消息都会被总线上的所有其他节点听到。该协议不包含原生**加密**，因此不提供**机密性**。

第三，协议包含一个循环冗余校验 (**CRC**) 字段。这听起来像一个安全特性，但它旨在检测由电气噪声引起的意外损坏，而不是恶意篡改。计算 CRC 的公式是公开的。攻击者在伪造恶意消息时，同样可以轻易地为其计算出正确的 CRC。类似地，CAN 帧中的确认 (**ACK**) 位仅仅确认了总线上*至少有一个*节点无 CRC 错误地接收到了消息。它并未说明是哪个节点确认的，也未说明该节点是否信任其内容 。

本质上，CAN 总线是一个公共论坛，没有发言者验证，没有私密对话，只有一个只关心语法而不关心事实的“事实核查员”。

### 弱点武器库

进入这个信任环境的攻击者拥有一个由简单但极具破坏性的攻击组成的强大武器库。

-   **[拒绝服务](@entry_id:748298) (DoS)：** 由于编号小的 ID 具有最高优先级，攻击者可以通过重复广播 ID 为 `0x0` 的消息来瘫痪整个网络。这个消息将永远赢得仲裁，从而有效“饿死”所有其他节点，阻止它们发送消息。这可能导致车辆或机器停摆 。

-   **欺骗与注入：** 通过冒充关键传感器或控制器，攻击者可以注入恶意指令。他们可以发送伪造的轮速传感器数据来混淆防抱死制动系统，或者发送“解锁车门”的指令。由于完全缺乏发送者认证，这一切都成为可能。

-   **重放攻击：** 标准的 CAN 帧没有“新鲜度”的概念，比如时间戳或[序列号](@entry_id:165652)。攻击者可以记录一次有效的传输——例如，解除警报的指令——然后在稍后的时间简单地重放它以达到其目的。接收方没有原生方法来区分重放的消息和合法的、新的消息 。

### 铸造数字盾牌

如果协议本身无法改变，我们该如何防御它？答案是在其上构建一个安全层，将一种新的、安全的语言嵌入到 CAN 消息自身的数据字段中。这涉及到使用密码学原语，它们就像安全性的基本构建块。

最常见的方法是在应用数据发送前，附加两个关键信息：一个**消息认证码 (MAC)** 和一个**计数器**。

**MAC** 提供完整性和认证。它的工作方式就像一个秘密握手。发送方和接收方共享一个密钥。发送方用该密钥将消息内容通过一个密码学函数处理，生成一个短小的、固定大小的标签——即 MAC。这个标签被附加到消息中。当接收方收到消息时，它用共享的密钥执行相同的计算。如果生成的标签与收到的标签匹配，接收方就知道两件事：消息在传输过程中未被篡改（完整性），并且它必定来自知道该密钥的人（认证）。这可以挫败欺骗和篡改攻击 。

**计数器**提供新鲜度并挫败重放攻击。发送方和接收方同意为每条发送的消息递增一个计数器。这个计数器值被包含在受 MAC 保护的数据中。接收方会记录它所见的最后一个有效计数器。如果一条消息到达时其计数器值小于或等于上一个值，那么它就是一条旧的、被重放的消息，并被立即丢弃 。

为了实现**机密性**，消息数据可以使用对称密钥算法（如高级加密标准 **AES**）进行加密。只有拥有[共享密钥](@entry_id:261464)的各方才能解密数据，从而保护数据免遭窃听 。

### 安全的代价

然而，增加这些安全特性并非没有代价。它引入了工程上的权衡，这优美地说明了设计现实世界信息物理系统所面临的挑战。两个主要成本是**时间**和**空间**。

首先，密码学计算需要时间。在高速车辆控制系统中，每一微秒都至关重要。让我们考虑一个每秒发送 $100$ 次关键更新的电池管理系统。为了保持稳定性，每个帧的安全处理必须在，比如说，$t_{\mathrm{budget}} = 800\,\mathrm{\mu s}$ 内完成。一个对称 MAC 计算可能只需要大约 $13\,\mathrm{\mu s}$。但更强大的公钥[数字签名](@entry_id:269311)，如提供不可否认性的 E[CDS](@entry_id:137107)A，情况又如何呢？验证一个 ECDSA 签名可能需要 $1500\,\mathrm{\mu s}$——对于我们的实时需求来说太慢了！这就是为什么系统设计者对高速率的操作数据使用快速高效的对称密码学（MAC 和 AES），而将缓慢、重量级的非对称密码学（数字签名）保留给不频繁但关键的操作，如验证固件更新，因为在这种场景下延迟是可以接受的 。

其次，安全数据占用了宝贵的空间。一个经典的 CAN 帧最多只能携带 $8$ 字节的数据。每一个用于 MAC 或计数器的字节都意味着无法用于应用数据。这导致了安全强度和网络带宽之间的直接权衡。

想象一下，我们需要系统能够抵御试图猜测 MAC 标签的攻击者。他们一次猜对的概率是 $p_{\mathrm{forge}} = 2^{-k}$，其中 $k$ 是标签的比特长度。如果我们要求这个概率小于一万亿分之一 ($10^{-12}$)，我们可以计算出所需的最小标签尺寸。结果表明，我们至少需要 $40$ 比特，即 $s = 5$ 字节 。

现在考虑这对网络的影响。如果我们在消息中添加一个 $5$ 字节的标签，我们可能会将总消息大小推高到超过 $8$ 字节的限制，迫使其被拆分成两个 CAN 帧。这几乎使该消息的开销翻倍。随着我们为了更强的安全性而增加标签大小（例如，增加到 $s=6$ 字节），在总线上发送的总比特数也会增加。我们可以精确计算**总线利用率**——即总线总容量被使用的比例。在一个典型系统中，将标签大小从 $5$ 字节增加到 $6$ 字节可能会将利用率从一个可控的 `0.94` 推高到一个超载的 `0.99`，从而违反系统的性能限制 。安全性不是绝对的；它是在保护与性能之间进行精细优化时的一个参数。

如果一个关键消息已经用满了全部 $8$ 字节的有效载荷，没有空间留给 MAC 怎么办？在这里，工程师们采用了另一个巧妙的技巧：他们照常发送数据帧，然后紧跟一个独立的、专用的**认证帧**。这个第二帧包含一个 MAC，该 MAC 覆盖了之前一批数据帧，从而在不修改原始、紧凑打包的消息的情况下提供了安全性 。这就是安全工程的精髓：在一个复杂的约束网络中寻找优雅而实用的解决方案。
